# 06 · 实战经验（真实项目里踩出来的做法）

这份文件不讲规则，讲**做事的方式**。前 5 节讲"怎么把墙报做出来"、`01`–`04` 讲"怎么把
HTML 变成逐元素对齐的 PDF/PPTX"，这里讲**在多轮返工里怎么不崩**：怎么接反馈、怎么收敛版面、
怎么交付、怎么在说"改好了"之前先证明它真的改好了。

规则可以照抄，经验只能被踩出来——这里把踩过的坑按"当时该怎么做"写下来。

## 1. 一轮 = 一次可回退的改动

- **改之前先快照**（`scripts/50_snapshot.py`）。墙报是"越改越乱"的重灾区：用户说第 4 节
  空、你缩了图，第 7 节就溢出。没有快照就没有退路，只有重做。
- **一轮只改一处维度**：图幅、文字量、页头高度、间距——一次动两个，门禁挂了就分不清是谁的事。
- **每轮结束都要有结论**：门禁 PASS / FAIL + 关键数字（余量、底边差、页尺寸）。
  "改好了"必须是数字，不是感觉。
- 迭代节奏：改 HTML → 重跑测量（一轮 40–90 s）→ 看数字 → 再改。**不要**手工去挪 PPT 坐标：
  那会让 HTML 与 PPT 从此不同源，下一次改 HTML 时 PPT 里的手工修正全部作废。

## 2. 用户反馈的处理流程

用户说的往往不是问题本身，而是一个**症状**。把它翻译成可验收的条件：

| 用户的说法 | 真正的检查项 |
|---|---|
| "这块看着空" | 该面板 slack（格底 − 内容最低点）> 阈值；或该列图幅没吃到栏宽 |
| "字压住了" | 文本框的垂直修正/行距；不是"把字号调小" |
| "和旁边对不上" | 成对元素（两张图、两个徽标）的宽度/基线是否一致 |
| "还是不满意" | 缺的不是修饰，是**内容**：先问"哪里不对"或按优先级列 3 个候选改写，让用户挑 |

三条纪律：

1. **逐条落实、逐条回报**：用户一次给 4 条要求，就回一张 4 行的表（要求 → 改法 → 依据），
   不要只回"已全部修改"。
2. **不确定就先查，不要凭记忆**：涉及"文件里到底有没有写"的问题，去读**交付物**（PDF/PPTX
   的渲染结果），不是读源文件里你希望它写的东西。二者不一致时，以交付物为准——你的记忆
   里"改了"，文件里可能没生效。
3. **改动可能影响别的部分**：改文案后重新跑门禁与一致性校验；只改文字也值得跑一次，
   因为换行点会变、面板高度会变。

## 3. 文案纪律（墙报不是论文缩写）

- **每个数字都要能在图上找到出处**；图注里的数字必须与**图内标注**一致（以图为准）；
  对不上时先请用户确认，不要自己挑一个。
- **一节只讲本节内容**：小结只能描述本节的图；跨节指代必须显式写"见 Fig. N（panel M）"，
  否则读者（和评审）会以为你在说另一张图。
- **不要借别人的数据当论据**：举例可以点方向，不要贴来源不明的数值。
- 引用体例统一（作者. 题目. *刊名* **年**, *卷*, 页码. DOI），只列**真的引用**的文献。
- 术语首次出现给全称 + 缩写，之后统一；中英混排时标点与空格统一（同一篇里不要两种写法）。
- 文案精简是**最后**的旋钮，不是第一个：先看是不是图太小/面板划分不合理，再删字。

## 4. 版面收敛：按这个顺序动旋钮

1. **图幅**：溢出先缩该栏图（等比），留白先放大该栏图到栏宽。图是版面的主体，动它最有效。
2. **面板/元素间距**：栏内 20 px、面板内 9 px 这类小间距是最后 20–40 px 的微调旋钮。
3. **文字**：删 1 行 ≈ 省 27–35 px（正文行高决定）。删整段之前先删重复句。
4. **页头高度**：改了页头（横幅、标题块、指标行）**必须**同步 `.content` 与 `.col` 的高度，
   否则整版下方空一条或底部被裁。
5. **改完必须重算**：`Σ栏宽 + Σ栏间距 = 画布宽 − 2×页边距`；栏区左右留白之差 ≤2 px。

**"不留白"要量化**：`slack = 面板底 − 面板内内容最低点`（DOM 实测，不是看图）。目标 0–40 px；
超过阈值就把该栏的图放大到栏宽，或补一句有实质内容的说明（不要灌水）。
三栏底边必须对齐（差 ≤2 px），底部留边距 ≥50 px——底部留白是"设计"，不是"没做完"。

## 5. 图与图：成对就要对得上

- 两张图放在一起对比时，**同宽**（宽高比不同就不能同高，硬同高会变形）。用户会一眼看出来
  "这张比那张小"。
- 一张合图 + **两条图注**可以保住原图号，避免全文重编号与交叉引用失配。
- 素材常带**不对称白边**（左 7 px / 右 99 px 这种），版面上会被读成"右边留白太多"：
  裁到墨迹包围盒 + 固定边距，裁完同步改 HTML 的 `width/height`。
- 换图/裁图后逐条核对：图注数字、图内标注、正文里引用它的那句话。

## 6. 交付纪律

- 三件套同版本同名：`poster.html`（真源）、`poster.pdf`（送印）、`poster.pptx`（可编辑）。
- 交付前 30 秒自检：门禁 PASS → 一致性校验 PASS → PDF 单页且尺寸正确 →
  浏览器残留进程 0 → 提醒用户"PPTX 若开着请**不保存关闭**后重开"。
- 用户开着 PPTX 时写入会失败（Windows 文件占用）：先重试，仍失败就请用户关闭并说明"不要保存"。
- **备份即交付的一部分**：每轮前后各一份快照，目录里放一句说明（备份策略），
  用户回退时不用问你。

## 7. 沟通纪律

- 回报用表格：**校验项 | 结果**。用户要看的是数字与结论，不是过程。
- 不要承诺"完全一致"：浏览器 / LibreOffice / PowerPoint 是三个渲染器，精确行距首行基线最多差
  约 8 px（实测 ≤6.4 px）。说清"可接受的差异范围"，比事后解释为什么差 6 px 好得多。
- 出现异常先看**残留进程**：卡顿、打不开别的程序、第二次连接失败，常见原因是上一轮浏览器
  没关干净（绝不用 headless，见 `@references/04-operations.md`）。
- 自己不确定的边界要主动说（例如某类元素表达不了），给出替代方案，不要静默降级。

## 8. 交付前自我怀疑清单

- [ ] 每节都**只剩**它自己的内容？跨节指代都写了图号？
- [ ] 每个数字都能在图/文献里找到？图注与图内标注一致？
- [ ] 三栏底边对齐、每格 0–40 px、底部留边距 ≥50 px？
- [ ] 每张图的 `width/height` 与源图纵横比一致（≤0.5%）？成对图同宽？
- [ ] 门禁 + 一致性校验都跑在**最终那版文件**上？（不是上一版）
- [ ] 交付文件里的文字与 HTML 里的一致？（PPT 是重新生成的，不是旧文件）
- [ ] 备份、图片授权留痕、编号框、署名与单位齐全？
- [ ] 有没有"看起来对但其实没跑"的检查？（选择器 0 命中、跳过当通过、
      验证对象是 HTML 而不是 PPTX——见 `@references/07-pressure-matrix.md`）

## 9. 什么时候该说"做不到"

明确列出边界，比含糊地"尽力了"更专业：

- 浏览器与办公软件对精确行距/字距的处理不同 → 复杂换行点的段落无法保证逐字一致。
- OOXML 表达不了的效果（`box-shadow`、缩放的 transform、部分 CSS 滤镜）→ 只能告警或近似。
- 图片授权、合作者姓名、涉密数据 → 先确认再上墙（`@references/05-prepare.md` §4）。

把"做不到"和"需要用户决定"的部分提前说清楚，剩下的部分才有底气说"已验收"。
